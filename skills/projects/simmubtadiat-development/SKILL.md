# SIM Mubtadiat Development

Pesantren management app (santri, pengajar, penilaian, absensi). Owner: jarvis. Live at https://reviewtechno.me (nginx → 127.0.0.1:8080). Repo: git@github.com:rezaulin/simmubtadiat.git (SSH key works, push from server).

## Stack & layout
- Backend: Go (chi router, pgx/v5). `main.go` = routes; `models/` = data layer; `handlers/` = HTTP.
- Frontend: Vite multi-page — entries in `frontend/*.html`, logic in `frontend/src/js/*.js`, builds to `public/dist`.
- Deploy: Docker Compose in /opt/simmubtadiat. Containers: `simmubtadiat-app-1` (port 8080), `simmubtadiat-db-1` (postgres:15).

## Editing gotchas
- **Go AND frontend JS files use CRLF endings.** The `patch` tool's fuzzy matching often fails on multi-hunk CRLF patches; fall back to Python `str.replace`, reading/writing with `newline=""` to preserve CRLF. When patching JS via execute_code with multiple old/new pairs, verify each one actually matched — a batch of LF-normalized old_strings can silently match nothing against a CRLF file (check "patched:" vs "NOT FOUND" output before writing).
- `go build ./...` fails with PRE-EXISTING errors in `scripts/` and `tmp/` (duplicate mains, stale APIs) — noise. Build only the app: `go build -o /tmp/test .`
- Frontend JS is plain ESM, one module per page (`<script src="./src/js/x.js" type="module">`).

## Database
- Access: `docker exec simmubtadiat-db-1 psql -U mubtadiaat -d mubtadiaat_db` (creds from /opt/simmubtadiat/.env; never print DB_PASS).
- Migrations: numbered `migrations/NNN_name.sql`, idempotent (IF NOT EXISTS / ON CONFLICT), auto-run on container start by `./migrate-runner migrations`. Add the next number; never edit applied migrations.

## Domain model (academic calendar)
- `tahun_ajaran` e.g. '2026/2027'; `tahun_hijri` e.g. 1447. Active values in `settings` table via GET/PUT `/api/settings/umum`. **`tahun_hijri_aktif` is a PAIR string** like `1447/1448` — one tahun ajaran spans two Hijri years (owner rule: "1 tahun ajaran ada 2, kayak Masehi 2025/2026, begitu juga Hijriyah 1447/1448"). Any `parseInt`/numeric-input binding must handle the slash first; rekap.js prefills only on `/^\d+$/`, settings.js calendar prefill uses the second (running) year, so users never switch year settings mid-year. Month dropdown options are RANGE-DRIVEN (owner correction 2026-08): `loadKalenderRange()` fetches the saved semester ranges first, and the dropdown lists ONLY months from Smt-1 start month through Smt-2 end month (e.g. 11 months for TA 2026/2027), with the 24-month pair list only as fallback when no calendar exists for the active TA.
- `kalender_semester_hijri`: Semester 1 & 2 ranges entered in HIJRI dates (tgl/bulan/tahun). Frontend computes Gregorian equivalents (`masehi_mulai/selesai`) via Intl islamic-umalqura before saving. See references/hijri-calendar.md.
- `kalender_kuartal`: derived sync table (kwartal 1–4 per tahun_ajaran) consumed by absensi-sesi lock & rekap; rebuilt automatically on semester save.
- Absensi sesi (per-date, Masehi): semester resolved by kalender_kuartal range lookup.
- Absensi manual bulanan (per Hijri month): `semester` column resolved by month OVERLAP with the semester range (`SemesterDariBulanHijri`, since 2026-08 — the old day-15 heuristic silently dropped months whose semester starts mid-month, e.g. Smt 1 beginning 17 Syawal lost all of Syawal); backfilled on every calendar save. Stray/out-of-range rows: see sim-mubtadiat references/academic-domain-model.md → "Forcing stray manual-attendance rows" before deleting or ignoring them — they are often Hijri-year typos the owner wants force-corrected.
- Penilaian: kuartal 1/3 = Tamrin, 2/4 = Ujian; semester lock via `penilaian_status`.

## Debugging gotchas (production)
- **"Server is right but owner's phone still shows the old UI" → verify server truth FIRST, then bump the Service Worker cache.** Diagnostic order (2026-08, background pattern): (1) curl index.html and confirm it references the NEW hashed asset filenames; (2) download those hashed files to a temp file and grep for the new CSS rule / element IDs; (3) confirm new static files (e.g. `/hero-pattern.jpg`) return 200. If all green server-side, it's device-side cache — fix by bumping `CACHE_NAME` in `frontend/public/sw.js` (e.g. `mubtadiaat-cache-v15` → `-v16`) and redeploying: on `activate` the SW deletes every cache whose name ≠ CACHE_NAME, so devices pick up fresh files on the next visit. The SW itself is served `no-cache` by the Go server (the `r.URL.Path == "/sw.js"` branch in main.go), so the bump always propagates. Then tell the owner to fully close & reopen the app (or open once in a plain browser tab so the new SW installs). Cloudflare `cf-cache-status: HIT` on hashed filenames is NOT the culprit (hash changes every build, so HIT still serves the new file).\n  - **PRECACHE TRAP — bumping CACHE_NAME alone does NOT fix a page listed in `urlsToCache` (hit 2026-08-27, `rapot.html`).** `sw.js` precaches an explicit list (`urlsToCache`) that historically included `/rapot.html` AND `/dist/rapot.html`. A precached page is served from the SW's OWN stored copy, so a fresh deploy never reaches the user even though `curl` + container md5 both show the new bytes AND CF returns `cf-cache-status: DYNAMIC` + `cache-control: no-cache` (CF innocent). Symptom: owner insists \"gak berubah\" after several deploys while every server-side check is green. FIX = BOTH steps, not just the bump: (1) REMOVE the changed page from `urlsToCache` so the network-first `fetch` handler always pulls it fresh; (2) bump `CACHE_NAME` so `activate` purges the old cache. The generic `fetch` handler is already network-first — only pages hard-listed in `urlsToCache` get frozen. Keep `urlsToCache` minimal (index/style/logo/favicon), never per-feature HTML you'll iterate on. Diagnostic tell: server bytes verified new + `cf-cache-status: DYNAMIC` + owner still stale → grep `frontend/public/sw.js` for the page in `urlsToCache` FIRST.\n- **Chromium auto-render/measure OOMs on this 2GB VPS (~250MB free)** — Playwright/`--single-process` chromium gets SIGKILL'd (exit -9) mid-run when trying to render rapot.html to measure pixel positions. Do NOT burn rounds retrying; it's a RAM ceiling, not a code bug. For print-layout tuning that needs pixel precision (e.g. aligning identity columns to a grid), the owner's phone print-preview is the source of truth — make one CSS change, deploy, ask the owner \"pas / kurang / kejauhan\" and iterate on his feedback rather than server-side measurement. Ask for a rough magnitude (\"kurang dikit\" vs \"kurang banyak\") to converge in fewer rounds instead of nudging px by px.
- **Long deploys run in background with notify_on_complete=true** — `docker compose build app && docker compose up -d app` takes minutes on this VPS. Foreground commands that look like they spawn a server/watcher get rejected as long-lived; wrap the whole commit→push→build→up→health-check chain in one background=true command with notify_on_complete=true, then continue other work; the system notifies on exit. Verify after the notification, don't assume. **False-positive case (hit 2026-08-23):** even a FAST foreground `docker compose up -d --build app` (image already built, returns in seconds) got rejected as "appears to start a long-lived server". `up -d` detaches and exits — it is NOT long-lived. Workarounds that worked: wrap the command as `sh -c 'docker compose up -d --build app'` so the heuristic doesn't pattern-match the bare command, or just run with background=true.
- **Cloudflare caches UNHASHED static assets (~4h, `max-age=14400`, `cf-cache-status: HIT`)** — replacing a file with the SAME name (icons, logos, manifest images) leaves CF serving the old bytes even after a full redeploy; the container copy is correct but HTTP returns stale. Signature: local/container file verified new, `curl` still old + `cf-cache-status: HIT`. Fix: rename the asset (e.g. `-v2` suffix) and update every reference (`grep -rn` across HTML/manifest/JS) so the URL changes — that bypasses the cache instantly without needing a CF purge. Vite-hashed JS/CSS are immune (hash changes per build); this trap is only for plain-named statics. Real case (2026-08): PWA icons turned teal locally but stayed black over HTTP until renamed `icon-*-v2.png`.
- **App logs do NOT show SQL error text for a failed POST** — `docker logs simmubtadiat-app-1` only shows the request line + 500. To find the cause, grep the access log for 5xx on the endpoint (`grep -i "hijri-semester" | grep 500`), then **reproduce the SQL directly**: run the transaction's statements step by step via `docker exec -i simmubtadiat-db-1 psql -U mubtadiaat -d mubtadiaat_db -v ON_ERROR_STOP=1 <<'EOF' ... EOF` (BEGIN → each statement → ROLLBACK). The failing statement names itself.
- **LATERAL/subquery alias pitfall (real bug, 2026-08):** in the kalender_kuartal sync query the SELECT used `k.tahun_ajaran` while `k` was only the LATERAL `(kuartal, idx)` value list — the column lived in the subquery alias `base` → 500 on every calendar save. Rule: when writing multi-alias Postgres SQL inside a Go tx, run the FULL SQL in psql first with sample data BEFORE building + deploying, not after.
- **"Same value shows in two UI sections" bug pattern (2026-08):** user saw one izin count in BOTH raport semester sections. Cause was not data — the backend returned one annual aggregate map and the frontend rendered it N times. Diagnose by grepping the frontend render calls for a shared map variable passed to multiple section-renderers; fix by returning per-section aggregates from the backend and passing the right slice to each section.
- **Vision tool may be unavailable** (provider error on vision_analyze). OCR fallback: `tesseract /root/.hermes/cache/images/<img>.jpg stdout -l ind+eng`. Improve odds with PIL preprocessing: crop the region of interest, upscale 3–4× (LANCZOS), `ImageOps.autocontrast`, `ImageOps.invert` for light-on-dark text; try `--psm 4/6/11` and TSV output (`--psm 6 tsv`) to get word coordinates for layout reconstruction. **When OCR still can't read parts (icon-based headers, low contrast), fall back to PIL PIXEL STATISTICS to infer structure instead of giving up**: dominant-color Counter (palette → identify light/dark/brand zones), avg brightness, horizontal mirror diff (low diff = symmetric layout), and edge density % (neighbor-diff threshold ~60; >40% = detailed pattern/ornament, <10% = flat) — this combo identified a screenshot's layout & classified an ornament pattern without any text extraction (2026-08). Then report honestly what you tried and what remains unreadable, and ASK the user for that specific part instead of guessing (owner will ask "Apa ocr mu mati?" — answer with evidence of attempts). Cross-check OCR'd digits against the DB.
- **Verify UI claims before stating them (owner caught this, 2026-08):** agent told the user "klik tombol Generate Khos" — no such button exists; the generate endpoints (`/api/penilaian/generate-khos`, `/generate-bayan`, `/generate-am`) are called INSIDE `saveAll()` (the "Simpan Semua" button) in frontend/src/js/penilaian.js. Before telling the user to click/enter anything, grep the page's HTML + JS for the element (`grep -n "generate" frontend/penilaian.html frontend/src/js/penilaian.js`). The real recalc path: Penilaian → pick bagian → Simpan Semua (see also: stored scores are snapshots — logic fixes don't retroactively update nilai_khos/nilai_bayan rows; mechanics + audit checklist in skill `sim-mubtadiat` references/academic-domain-model.md → "Recalculating stored scores").
- **"Corrections don't work / nilai hilang" is often stale scores from pindah bagian, not a logic bug (2026-08):** santri who change bagian/class leave orphaned score rows — duplicate `nilai_bayan` (unique key includes bagian_id) and `nilai_khos`/`nilai_kuartal` still bound to the OLD class's mapel while regen reads the CURRENT class's mapel. Also: absence-based Akhlaq corrections are a SILENT no-op if no mapel has kategori `akhlaq_perilaku` (prod shipped with none). Root `nilai_kuartal` staleness is a data-ownership question — STOP and ask the owner (mid-TA class change vs migration artifact) before relinking/deleting raw marks.
- **Background processes run under /bin/sh, not bash** — `source .env` fails with exit 127 (`source: not found`). In backgrounded terminal commands, load env POSIX-style instead: `export $(grep -E '^(DB_USER|DB_PASS|DB_PORT|DB_NAME)=' .env | xargs)`.
- **Proving business logic end-to-end — `go test` is unusable in this repo**: stale test files in `models/` (alumni_koersi_test, pencarian_pengabdian_test, perpindahan_test, santri_khidmah_test) fail to COMPILE with outdated signatures, so any `go test ./models/` dies before running. This is the accepted way to answer "does this logic actually work?" with proof, not code-reading. Owner values this — he asks "apakah code untuk itu sudah berfungsi?" expecting verification, not reassurance.
  - **How to RUN throwaway Go tools (updated 2026-08-23): `go run` in the app container is DEAD** — the deployed image is `alpine:latest` WITHOUT a Go toolchain (`docker compose run app ... go run` → `go: not found`), and the host has no Go either. ## Raport layout & Arabic typography fixes

Real issue (v19–v24): Arabic script letters with **descenders** (خ ج ح ع غ ي ق س ش ص ض) were visually touching bottom grid lines in raport footer table, even though CSS had `padding: 2px 6px`. Reference physical report photos showed a minimum **~0.74mm** gap needed for clean appearance. Our rendered PDF only provided ~0.53mm gap at screen DPI, creating a mismatch when printed on F4/A4 paper.

**Root cause analysis:**
- Tesseract OCR confirmed descender letters extend below baseline by 3–4px at typical densities
- PyMuPDF rendering + PIL pixel analysis measured actual gaps: found 0.37mm touch-point in initial deploy vs 0.74mm reference minimum
- Problem persisted even with correct padding because **line-height was too tight** (1.15), letting descenders hang too low

**Solution pattern (combined approach, used in v24):**
```css
.rapot-sheet td, .rapot-sheet th {
    /* BEFORE */
    padding: 2px 6px;         /* symmetric padding */
    line-height: 1.15;        /* compact, lets descenders protrude */
    
    /* AFTER */
    padding: 1px 8px 4px 6px; /* asymmetric: more BOTTOM space where descenders live */
    line-height: 1.22;        /* minimal +6% increase reduces effective descender depth */
}
```

**Why this works:**
- Asymmetric padding adds explicit clearance BELOW text without increasing total row height significantly
- Small line-height increase reduces relative descender depth while keeping rows within page limits
- Combined: +0.2–0.3mm additional gap = target ~0.7–1.0mm meets reference standard

**Implementation workflow:**
1. Patch the exact CSS rule in `frontend/rapot.html` using fuzzy patch tool (ensure you match the comment block if padding appears multiple times)
2. Bump Service Worker cache in `frontend/public/sw.js` (`CACHE_NAME = "mubtadiaat-cache-vXX"` → increment version)
3. Commit both changes separately, push to GitHub
4. Deploy via Docker Compose with health check wait
5. Verify via curl on `https://reviewtechno.me/sw.js` confirms new CACHE_NAME
6. Generate visual comparison proof: render current rapot to screenshot using Playwright or browser snapshot, crop bottom table section, add measurement annotations using PIL ImageDraw (red boxes marking min gap locations)

## Feature workflow

### Recurring bug patterns found this codebase (2026-08-27)
- **INSERT placeholder/column mismatch = silent total failure.** `models/santri.go` had `INSERT INTO santri (...19 cols...) VALUES ($1..$18, 'aktif', ...)` — a literal `'aktif'` in the middle shifted every subsequent `$N` so the placeholder count didn't match the column count → Postgres `INSERT has more expressions than target columns (SQLSTATE 42601)` on EVERY row → import santri had been failing 100% silently. When an INSERT has an inline literal mixed with `$N` params, count columns vs (placeholders+literals) by hand. A throwaway Docker verifier (see the Go-tool recipe above) surfaced this instantly — the app logs only showed 500s.
- **Batch import: prefer PARTIAL over all-or-nothing (owner pref 2026-08-27).** Owner wants valid rows committed and only bad rows skipped + reported (Baris/Nama/Alasan), NOT the whole batch rolled back. Pattern: commit per-row in its own tx inside the loop, collect failures into `res.Errors[]`, return `sukses`/`gagal`/`errors` even on partial success (HTTP 200). Frontend renders a red table of skipped rows + a 📋 Salin (copy tab-separated) button — owner asked for on-screen + copyable, not a downloaded file. `humanizeDBError` maps unique-violation to friendly text ("NIK sudah terdaftar").
- **Assign-on-create must be ONE backend transaction, not a second API call.** Adding a santri with a bagian: send `bagian_awal_id` in the POST `/api/santri` body — `CreateSantri` already sets `bagian_id` + inserts `riwayat_bagian` atomically. The old frontend omitted `bagian_awal_id` and instead fired a SECOND call to `/api/perpindahan/naik-kelas`, which was unreliable → santri stuck in "belum di kelas". Rule: if a create handler already accepts the association field, pass it in the create payload; don't chain a follow-up mutation.
- **`nama_indo` column for Indonesian mapel names (migration 050).** `mata_pelajaran.nama_indo` holds the Indonesian name shown in Riwayat Akademik + Penilaian, while RAPORT CETAK keeps the Arabic `nama_kitab`. Fallback when `nama_indo` empty = show Arabic as-is (owner rejected the `kitab-translate.js` dictionary approach — it leaked untranslated). Riwayat mapel order = `ORDER BY m.urutan` (same as raport). Frontend fills the "Nama Indonesia" field in Data Kelas → Kelola Mapel.
